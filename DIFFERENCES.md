# Deliberate differences from GeoGebra

Behaviour that differs from GeoGebra on purpose is recorded here, with the
reason. A difference that is not listed here is a bug.

Mismatches for recorded cases are listed in `crates/geo-golden/known-gaps.toml`.
The tables below also record unsupported command forms and their prerequisites.

| Area | GeoGebra | geokernel | Reason |
| --- | --- | --- | --- |
| Objects created by a command with several results (`Tangent`, `AngularBisector` of two lines; `Focus`, `Vertex`, `Directrix` and `Tangent(P, conic)` of a conic) | The set of labelled objects can change over time: a result that is undefined when the command runs gets its label only once it becomes defined. | The objects are fixed when the command runs. All results that are defined at that moment are created (`t_{1}`, `t_{2}`); when at most one is defined, only that one (or the first) is created under the plain name. For `Focus`, `Vertex`, `Directrix` and `Tangent(P, conic)` the type of the conic when the command runs decides the set: a conic that is degenerate or of another type then (a hyperbola has two defined vertices of four, a parabola one focus and one directrix, a point on the conic one tangent) keeps that set when it later changes type. | A construction whose list of objects depends on the history of moves cannot be replayed or saved reliably. |
| `Diameter(line, circle)` of an undefined circle (`conic-diameter-007`) | The line keeps the value it had while the circle was last defined. | The line is undefined. | The GeoGebra value depends on the history of moves and no longer belongs to any circle. |
| Predicates on undefined circles (`predicates-equal-017`, `predicates-tangent-013`) | An undefined circle keeps the conic matrix of its last defined state, and `AreEqual`, `IsTangent` still use it. | The circle has no value, so the predicate has none either. | The matrix depends on the history of moves. |
| Points at infinity as inputs of `AreEqual` and `ClosestPoint` (`predicates-infinity-001`, `points-infinity-001`) | The intersection of parallel lines is a defined point at infinity; `AreEqual(S, S)` is true and `ClosestPoint(circle, S)` projects its direction. | Points at infinity are undefined, so `AreEqual(S, S)` is false and `ClosestPoint(circle, S)` is undefined. | The kernel keeps no homogeneous weight on points. `AreCollinear`, `AreConcyclic`, `AreCongruent` and `AreEqual(S, F)` with such a point agree in the same case. |
| `AreConcyclic` of intersection points (`predicates-homogeneous-001`) | Reads the homogeneous coordinates, whose weight is the raw cross product of the lines. | Assumes weight 1. | Same reason. Only this one configuration is known to differ; other predicates and `ClosestPoint` on such points are covered by cases that agree, but whether the assumption holds in general is not verified. |
| `ClosestPoint(vector, point)` and `ClosestPoint` of two segments or rays | `GeoVector` is a `Path` in GeoGebra (source: `GeoVector implements Path`), so a vector is accepted. Two segments or rays are `GeoLine`s and give `AlgoClosestPointLines`. | Rejected with an error. Only two lines are supported (their intersection, as `AlgoClosestPointLines` is `AlgoIntersectLines`). | The kernel stores no start point for a vector. Not observed with a golden case: a case script that the kernel cannot load fails the script corpus test, so these forms stay unverified. |
| `TriangleCenter`, `ClosestPointRegion` | Available. | Not implemented. | `TriangleCenter` needs the large `AlgoKimberlingWeights` table. |
| Objects created with a polygon (`Polygon(...)`, `Vertex(p)`, `InteriorAngles(p)`, `Angle(p)`) | At creation GeoGebra labels only the sides of `Polygon(A, B, C, ...)` that are defined then; for `Polygon(A, B, n)` nothing besides the polygon when `round(n) <= 2`, and no sides when `A` or `B` is undefined (all observed with the harness). Later, `AlgoPolygonRegularND.updateOutput` creates and labels more vertices and sides when `n` grows past the number it has; `Vertex(p)` and the angle commands create more outputs when `p` gets more vertices (and `Vertex(p)` of a polygon that is undefined at creation starts with one). Whether an unlabelled side is labelled once it becomes defined is not recorded: the harness only sees the labels given at creation. | The objects are fixed when the command runs and follow the labelling at creation: the sides of `Polygon(A, B, C, ...)` that are defined then; for `Polygon(A, B, n)` nothing besides the polygon when `round(n) <= 2`, else every new vertex, and the sides only when `A` and `B` are defined then. The polygon itself still has all `round(n)` vertices (`Construction::vertices`), and its area, perimeter and centroid use them; only the extra point, segment and angle objects are missing. | Same as for commands with several results: the list of objects must not depend on the history of moves. |
| Growing coordinate lists (`Point(list)`, `geomextras-pointlist-007`) | Setting `a` to `0` in `l = If(a > 0, {{a, 2}}, {{a, 2}, {3, 4}})` appends the point `A = (3, 4)`. Returning `a` to `1` keeps `A` undefined. | Only the point from the initial row is created. Existing output slots update or become undefined when their rows disappear. | Output labels are assigned when the command runs, as with polygon commands. Creating labels on update needs workbench journal and replay support. |
| Regular polygon with very many vertices | No limit on `n`. | `Polygon(A, B, n)` with `round(n)` above 1000 is refused when it is created, and the polygon is undefined while `round(n)` is above 1000 later. Otherwise the vertex count follows GeoGebra's `(int) Math.round(n)`, including its wrapping (`4294967299` gives 3 vertices) and `NaN` counting as 2. | A regular polygon creates `n` objects and computes `n` vertices on every update; a stray large number would stall the application. |
| Polyline through a point at infinity | The point counts as defined, so the length is not finite. | The point is undefined (the kernel has no points at infinity), so it leaves a hole and the length stays finite. | The kernel represents a point at infinity as undefined everywhere. |
| Vertices of a regular polygon whose `A` or `B` is undefined (`polygon-regundef-001`, `polygon-regundef-002`) | The new vertices keep their last coordinates, `(0, 0)` before the polygon was ever defined, and count as defined. | They are undefined. | The GeoGebra value depends on the history of moves and no longer belongs to any polygon. |
| Arguments of the polygon commands (`Polygon`, `PolyLine`, `Area`, `Perimeter`, `Centroid`, `Vertex`, `InteriorAngles`, `Angle` of a polygon or polyline) | Any expression, such as `Polygon(A, B, n + 1)`, `Vertex(p, 2 * k)` or `Polygon((0, 0), (1, 0), (0, 1))`. | Each argument is the label of an existing object or, for a number, a plain decimal literal such as `5`, `-2` or `3.5` (no exponent, sign `+` or words such as `inf`); an existing label always wins. | The script format has no expression parser for these commands; a definition must refer to objects. |
| `Intersect(k, k, 1)` (`intersect-itself-004`, `intersect-itself-005`) | The result is the first point on `k` by construction (`AlgoIntersectConics.getPointFrom1on2`), which can be an earlier intersection point `X` of `k`. `X` is not an input of the algorithm, so when only `X` moves the result keeps its old position until `k` changes. | The result always shows the current `X`; `X` is read as a hidden parent. | The GeoGebra value depends on the history of moves. |
| Creation-time flag of a circle intersection (`special` in `Def::IntersectCircles`) | `AlgoIntersectConics` decides when the intersection is created, from the positions at that moment, whether a point on both circles by construction is intersection 1, and keeps the decision. | The same; a rebuild from the definitions keeps the flag. A script cannot state it, so running the script with the free objects elsewhere can decide it otherwise and give other values. | The script syntax follows GeoGebra's commands, which have no such argument. |
| Elementary functions in expressions (`sin(a°)`, `gamma`, `acosh`, `round(a, 2)`) | Some values come from BigDecimal arithmetic (multiples of degrees in `sin`, `cos`, `tan`) or from Apache Commons Math (gamma, some inverse functions). | Plain `f64` arithmetic, Rust's standard functions and an own Lanczos gamma. `round(a, n)` of a value with an exact decimal (see the next row) uses that decimal; otherwise it rounds the shortest decimal form of `a` half up. | No dependencies, and Apache Commons Math is not GeoGebra code. The results differ at most in the last bits (well inside the golden tolerance), e.g. `sin(30°)` is `0.49999999999999994` instead of `0.5`. |
| A name that is not an object, such as `ab` when `a` and `b` exist | Split into a product of objects (`a b`). | In an ordinary expression rejected; a product needs a space or `*`. Only an upper-case `E` starts an exponent, so `2e3` is `2` times the name `e3` and falls under this rule. Inside an equation the name splits into a product of its letters as in GeoGebra, so `2xy = 1` is the hyperbola `2*x*y = 1`; only a name alone on the left of `=` stays whole, so `xy = 1` is an unknown name. | The meaning of an ordinary line would change when an object `ab` is created later; the equation form follows GeoGebra, where the letters of such a name are the variables of the equation. |
| Work of one exact decimal operation (`expr-decimal-027`) | `BigDecimal` arithmetic has no limit: `(1E-100001 + 1) - 1 + 0.1 + 0.2` is exactly `0.3`. Exponents outside the `int` scale throw (`(1E-999999999)^3`: "Underflow"; `1E-3000000000`: "Exponent overflow"), and a product such as `1E-999999999 1E-999999999` runs out of memory; each line is rejected. | The same arithmetic while one operation stays within bounds: a result of at most 100000 digits, a product or division of at most 10^7 digit products, and an exponent within Java's `int` range. An operation past a bound, and every operation after it in the same expression, is computed with doubles: the chain above with `1E-100001` gives `0.30000000000000004` (with `1E-5001` it gives `0.3`, as GeoGebra). The lines GeoGebra rejects for their exponent give the double result (`0`) instead of an error. | A hostile line must not use unbounded memory or time on every update. The golden topic `expr-decimal` covers the rules up to the bound, with one known gap past it. |
| Exact decimal of a free number that was set (`expr-exact-037`) | A number made from a decimal literal keeps the literal's decimal for exact arithmetic until its value is set (`GeoNumeric.setValue`, a drag, a slider), even to the same value. So the last bits of what reads it depend on whether it was ever set. | The same. `Construction::expression` hands out a free number's decimal, so a rebuild through the API keeps it. A script line states only the value: replaying a construction whose number was set gives the literal's decimal back and can change dependents in the last bits. | Same as the circle intersection flag: the script syntax follows GeoGebra's, which has no way to say that a number was set. The property tests compare against a first `set` of the number for this reason. |
| Expression syntax that is not supported | Degrees-minutes-seconds input (`30°15'`), gradians and `rad`, calls with square brackets (`sin[x]`), `xcoord(` and `ycoord(`, points written `(1 \| 2)`, comparisons, booleans, `¬` and `If`, complex numbers, functions beyond the built-in list, `1..2` as a list, `random()`. | Each is an error, and the line leaves nothing behind. | Not implemented. Comparisons and `If` need a boolean value kind and an undefined branch; `random()` cannot be checked against golden data. |
| Digits other than `0`-`9` | The parser takes digits of other scripts (Arabic-Indic, Devanagari, ...) in numbers. | Only ASCII digits make a number; other digits are an error. | Rare in practice, and the literal text is also the exact decimal, which needs ASCII digits. |
| `inf`, `Infinity`, `NaN` and `Undefined` as labels | Read as the constants ∞ and undefined, so they cannot be labels. | Accepted as labels. In an expression the name is still the constant; in a polygon command an existing label wins. | The polygon argument forms read plain labels and depend on this. |
| A function that reads a point at infinity, such as the intersection of two parallel lines (`expr-fnundef-008`) | The function stays defined; all its values are undefined. | The function is undefined. | The kernel has no points at infinity: such a point is undefined, as in the golden data, and a function is undefined when a point it reads is. |
| `1 / 0` inside the list commands (`lists-undef-*`, `lists-classes-015`, `lists-take-016`) | `1 / 0` is the defined value ∞, so `RemoveUndefined` keeps it and a point with an infinite coordinate, `Classes` computes its bounds with it (they come out NaN, −∞ and ∞, which the golden data records as undefined numbers), and `Take(l, m) + 1` with `m` past the end maps over the elements that the list kept from its last defined state. | The kernel has no infinity: `1 / 0` is undefined, `RemoveUndefined` drops it and a point with an infinite coordinate, the bounds of `Classes` stay finite, and an undefined list has no elements to map over. | Recording ∞ as undefined agrees with the golden data everywhere else (a value that is not finite shows as undefined); only these commands tell the two apart. |

## Opening construction files (`geo-import`)

| Area | GeoGebra | geokernel | Reason |
| --- | --- | --- | --- |
| `$point(x, y)` in the script language | The parser's `$point` follows the label rule: with a lower-case label the result is a vector. The XML expresses a lower-case point with `type="point"` on the `<expression>`. | `a = $point(1, 2)` is a free point whatever the label. `$vector(x, y)` is a free vector whatever the label, as in GeoGebra. | A saved file has lower-case points and upper-case vectors, and the script has to reproduce the right kind. |
| Which outputs a command creates, in a saved file | Labelled outputs are those that were defined when the command ran. | `{t_{1}, t_{2}} = Tangent(P, k)` creates exactly the outputs that have a label; an empty slot creates nothing. When both tangents from `P` are the same line at creation (`P` on the circle) the kernel still makes only the first, so a label for the second is an error and a file saved with both labels does not import that command. | The file states the labels, so the kernel does not decide. The limit is in `tangent_points` (`algo/lines.rs`). |
| `Distance(line, line)` read from a file | `AlgoDistanceLineLine` writes its inputs in the reverse of its computing order; `GeoLine.distance(GeoLine)` returns 0 for lines that are not parallel in either order, and tests "parallel" on raw coefficients, so for lines with coefficients near 1e-6 the order changes the value. | The importer reads the inputs as written, as GeoGebra's reader does, and reports the object in `mismatched` because the file's saved value is the pre-save one. | The importer follows what GeoGebra computes when it opens the file; `harness.sh reload` on the five affected files gives the importer's values. `known-import-gaps.toml` pins both values of each. |
| Unindexed `Intersect` in a file | GeoGebra keeps the permutation chosen by the first update. After a reversal the two saved labels can be in the opposite order from a fresh computation. | For a saved pair with two distinct points, reverse the indices when both saved coordinates match the opposite slots at the existing tolerance. All 24 `saved-firstmove` files agree after import. | The coordinates disambiguate the branch labels at load. Later edits still use the indexed kernel solver. |
| Undo and redo of conic intersections | A restored intersection can recover its branch assignment from its saved points. | Undo and redo rebuild the conic intersection from its script and replay the retained edits. A branch can change after replay if the original assignment depended on an intermediate position. | The workbench log coalesces edits and stores neither intermediate positions nor the conic pair's slot permutation and candidate history. Rebuilding from kernel definitions can carry the compact permutation. |
| Labelled second point at a tangent point | `avoidDoubleTangentPoint` retains the duplicate when the second point has a label. | The indexed circle intersection retains only the first point at tangency. The 12 cases `saved-doubletangent-001` through `saved-doubletangent-012` report only `P_{2}` as undefined. | Restoring the duplicate requires carrying the unindexed command’s labelled-output policy into the indexed solver. Each case is listed in `known-import-gaps.toml`. |
| Segments, rays, polygons in the saved-value check | A segment or ray is saved as its line only; a polygon or polyline has no saved value at all. | Lines are compared (up to a positive factor); the end points are the objects the segment was made from, and are compared as such. Polygons are not compared against the file. | Nothing else is in the file. |
| Circle radius in the saved-value check | The matrix `A0..A5` is saved, and the radius is only recoverable as a difference of terms of size about `cx^2 + cy^2`. | Centre compared at 1e-9; the squared radius at 40 * 2.2e-16 * (`cx^2 + cy^2 + |A2/A0|`) or the radius at 1e-9, whichever is looser. | The bound comes from the rounding of the matrix itself (about ten roundings of terms of that size, times four), not from 1e-9 of the squared terms. |
| Value saved in the file vs value computed | The file holds the values of the moment it was saved. | The kernel recomputes; every object whose value differs by more than `1e-9` relative is kept and listed in `Imported::mismatched` (the CLI prints it, the app counts it). | A disagreement is information, not a reason to drop an object. |
| Labels of polygon outputs | The file names the polygon, its sides and new vertices. | The kernel labels them itself (as GeoGebra does); a file label with no counterpart (a renamed side) is skipped with its dependents. | The kernel has no way to name the outputs of `Polygon`. |
| Buttons, checkboxes and input boxes (`button`, `boolean`, `textfield`) | Controls appear in the graphics view. Input boxes edit or redefine their linked object. | The algebra sidebar displays control captions. A free checkbox stays editable there when hidden in the graphics view. Input boxes retain the link and edit a free number or angle. | Control positions, unlinked text entry and editing or redefining other linked kinds through the input box are outside this import. |
| Object scripts on any saved element | `GeoElement.getScriptTags` writes GeoGebra Script or JavaScript for click, update, drag-end and change events. | The import and snapshot preserve the script text and event as inert data. A file with object scripts gets an import note. | The application does not execute imported scripts. |
| `<condition showObject>` | A boolean label or expression controls visibility, independently of the saved show flag. | The condition is restored after the objects it reads. The workbench and imported SVG use its boolean value. | Visibility is a presentation property and may read an object defined later in the file. |
| Saved 2D element types | `GeoElement.getElementOpenTagXML` uses the XML names in `GeoClass`. It writes `image`, `implicitpoly`, `polyline`, `locus`, `curvecartesian` and `numeric` with `<slider>`, among other 2D types. | Implicit polynomial equations and their coefficient matrices load as implicit elements. Polylines and loci rebuild from their commands, and `CurveCartesian(number, number, number, number, number)` rebuilds from its two coordinate expressions, local parameter and bounds. Free numeric sliders restore literal, expression-valued and one-sided bounds. The imported value and later edits are clamped to the applicable bounds. Missing or unsupported bounds produce an import note. | Slider handle placement, styling, animation and increments are not restored. The kernel has no drawable pen stroke, turtle or media object. Audio, video and embeds are outside scope because playback and hosted content are outside the geometry kernel. |
| Limits | None. | Unpacked XML at most 256 MiB, at most 4096 zip entries, at most 200000 items; beyond them an error. Only stored and deflated entries, no zip64. | Hostile input. |
| Constant expressions | An `<expression>` with no object in it is an independent object. | Read as a free object with the saved value; any identifier makes it an ordinary expression, which is skipped. | Same rule as GeoGebra's `isIndependent`. |
| Outputs that are undefined when a command runs, in a saved file | Have no label in the file. | Cannot be recovered: the importer reports them as skipped without a label. | The label is not in the file. |
| Expression syntax that is not supported (supersedes the row above of the same name) | Degrees-minutes-seconds input (`30°15'`), gradians and `rad`, calls with square brackets (`sin[x]`), `xcoord(` and `ycoord(`, points written `(1 \| 2)`, complex numbers, functions beyond the built-in list, `1..2` as a list, `random()`; lists compared (`{1, 2} == {1, 2}`) or combined with logic, lists in functions (`f(x) = {x, 1}`), lists as branches of `If`, a list as a coordinate (`(l, 1)`), `Sum(l, f)` with a list of frequencies, `Zip` and the other list commands not named here. | Each is an error, and the line leaves nothing behind. Comparisons, booleans (`true`, `!`, `¬`, `&&`, `\|\|`, `⊕`, `->`), `If`, list literals, element access `l(n)`, `Element`, `Length`, `Sum`, `Product`, `Min`, `Max`, `Mean`, `Reverse`, `First`, `Last`, `Sort`, `Append`, `Join` and `Sequence` are supported. | Not implemented yet; `random()` cannot be checked against golden data. |
| Constant booleans and lists (`t = true`, `l = {1, 2, 3}`) | Independent objects, with a checkbox for the boolean and an editable list. | An imported free boolean can be edited through its checkbox. Typed literal booleans and lists use the expression engine. | The checkbox is an editable definition with a Boolean result. |
| Very long lists | No limit on the number of elements. | A list whose evaluation needs more than 2^20 elements, nested ones included, is undefined while that holds (`Sequence(2000000)`). | A stray large count would stall the application and exhaust memory on every recompute. |
| `Sort` of values closer than `1e-8` | A `TreeSet` with a comparator that treats values within `1e-8` as equal (and points with such `x` by `y`), so the order of near ties depends on the insertion order and the shape of the tree. | Numbers and booleans by exact value, points by exact `x`, then `y`; undefined elements last. | The comparator is not a total order and cannot be reproduced by a sort; the difference is limited to elements within `1e-8` of each other. |
| Expression syntax that is not supported (supersedes the rows above of the same name) | Degrees-minutes-seconds input (`30°15'`), gradians and `rad`, calls with square brackets (`sin[x]`), `xcoord(` and `ycoord(`, points written `(1 \| 2)`, complex numbers, functions beyond the built-in list, `1..2` as a list, `random()`; lists compared (`{1, 2} == {1, 2}`) or combined with logic, lists in functions (`f(x) = {x, 1}`), a list and a value that is no list as branches of one `If` (`If(a > 0, {1}, 2)`, where GeoGebra gives an undefined list when the number is chosen), a list as a coordinate (`(l, 1)`), `Sum(l, f)` with a list of frequencies; `Last` of a function (only a hand-drawn line graph fits); `Union`, `Intersection` and `Remove` with polygons (also a polygon and a list of points); `RandomElement`, `SelectedElement` and `SelectedIndex`. | Each is an error, and the line leaves nothing behind. | A list that is undefined inside an expression (`If(a > 0, l) + 1` with a false condition, `l(n)` past the end of a list of lists) | The helper list is a `GeoList` that `setUndefined` does not clear: it keeps the elements it last held (or a template element, a list holding one undefined number), each set undefined, and what reads it element by element gives a defined list of undefined elements (`Length` of it counts them). | The list is undefined, and so is what reads it. | Very long lists (supersedes the row above of the same name) | No limit on the number of elements or on the work of one update: `AlgoSequence` builds as many elements as its range gives and stops only when free memory is critical, and is undefined only when the count `(to - from) / step` is infinite; `AlgoSequenceRange` is undefined only past `MyMath.LARGEST_INTEGER` or with a zero step or one of the wrong sign. A step that cannot reach the end (within `Kernel.MIN_PRECISION` of it, or too small to change the variable) never ends. | One evaluation of one object may build at most 2^20 elements in all, across every nesting level and counting lists that are built and dropped again (an inner `Sequence` for each value of an outer one, the lists a `Sum`, `Length` or `First` reads in a loop). | Very long lists and costly evaluations (supersedes the rows above named "Very long lists") | No limit on the number of elements or on the work of one update. `AlgoSequence` builds as many elements as its range gives and stops only when free memory is critical; a function applied for each value costs its whole tree each time. `AlgoSequenceRange` gives an undefined list past `MyMath.LARGEST_INTEGER` or with a zero step or one of the wrong sign, and `AlgoSequence` one for an infinite count `(to - from) / step`; such a list inside another is an undefined element. `Sequence(n)` counts to `(int) Math.round(n)`, so a count past `int` wraps and one of 0 or less is empty. A step that cannot reach the end (within `Kernel.MIN_PRECISION` of it, or too small to change the variable) never ends. | The ranges GeoGebra refuses give the same results (golden cases `lists-limit-*`): an undefined list, an undefined element of a list around it (`{Sequence(1, 1E20), {1}}` is `{?, {1}}`, and `Sequence(Sequence(1, 1E20), k, 1, 1E6)` a million undefined elements, built and counted like any others), and `Sequence(n)` wraps like `(int)` (`Sequence(1E20)` is `{}`, `Sequence(2^32 + 3)` is `{1, 2, 3}`). Beyond that, one evaluation of one object has two bounds of its own, and past either it stops at once and the whole object is undefined, not only the list being built: at most 2^20 elements built in all, nested lists and lists built and dropped again included (memory: `Sequence(2000000)`, `Sequence(Sequence(j + k, j, 1, k), k, 1, 1E5)`, `Sequence(j, j, 0, 1, 1E-300)`), and at most 2^25 units of work (time). A unit is about one node of a tree: the tree of the object once (functions expanded), the body of a `Sequence` again for each value of its variable, a step of the list code (counting, filling, copying or reading an element), and in exact decimal arithmetic on numbers too long for the inline forms (77 digits) a digit handled or four digit products. | Very long lists and costly evaluations: the work charged (supersedes the row above named "Very long lists and costly evaluations") | As in the row above: no limit on the number of elements or on the work of one update. | The ranges GeoGebra refuses give the same results, and the bound of 2^20 elements built in one evaluation is unchanged (see the row above). The bound on work charges what the evaluation does, as it does it: at most 80 000 000 units for one evaluation of one object with lists, about 0.3 s of a release build (a unit is about 3.5 ns, measured; the slowest evaluations near the bound take 0.24 to 0.38 s: 0.36 s for quotients by a 3 000-digit number without zero digits and 0.38 s for `Max(L) + k` over a list object of 10 000 elements, about 4.8 ns for each element read). A node visited is 3 units in the full evaluation and 1 in `evaluateDouble`, a power 8 more and a function of a number 4 more; only the branch of an `If` that is taken is visited; a function sampled or expanded is charged its nodes at each call. A step of the list code (counting, filling, copying or reading an element) is a unit, a sort `n (1 + log2 n)`. Each exact decimal operation is charged its measured time: 3 units for a sum, product or rounding of coefficients up to 38 digits, 30 up to 77 digits, 100 for a quotient, 40 for the exact decimal of a double and 90 to 180 for the double of a decimal; on longer numbers 100 units and a unit for each digit handled (64 digits that are only scanned or copied whole), each 24 digit products of a product and each 2 of a quotient; digits without zeros were measured as well as numbers like `1 + 1E-3000`. Every node is checked before it runs and every loop of the list code before it starts, so one evaluation goes past the bound by at most the exact operations of one node (at most four, 2 467 067 units in all, about 9 ms; at most 88 071 units in the cases measured). A list object read in a body (`L(k)`, `Element(L, k)`, `Length(L)`, `Max(L)`, `First(L, k)`) is read in place, as upstream reads the `GeoList` itself: it is neither copied nor counted against the element bound (each read was, so `L = Sequence(k^2, k, 1, n)` and `Sequence(L(k) + 1, k, 1, n)` were undefined from about n = 2 000); each element read is a unit of work, so a body that reads a whole list for each value is charged every element it reads: with `L = Sequence(k^2, k, 1, 10000)`, `Sequence(Max(L) + k, k, 1, 10000)` reads 10^8 elements and is undefined after 0.38 s (at 3 000 values it is defined); a list that holds such a list is copied and counted when it is stored. So ordinary lists are defined: `f(x) = 3.7 x (1 - x)` nested nine times at 10 000 values is about 1 million units, and `Sequence(1.0000001^999999 + k, k, 1, 10000)` 62 million (0.26 s); `Sequence(k * 1.0001^365, k, 1, n)` is undefined from about n = 31 700, the function `g` of about 240 000 nodes at 10 000 values stops after 0.27 s, and `Sequence(1 / 3 + 1 / 7 + 1 / 9 + 1 / 11 + 1 / 13 + 1 / 17 + 1 / 19, k, 1, 1048576)`, which took 7.4 s, is undefined after 0.29 s. The bound is per evaluation of one object: an update that recomputes several dependent objects may take up to that much for each of them. It covers objects with lists only: an object without lists is bounded only by the static cost of its tree and the caps of each exact operation, so a balanced sum of 2^18 copies of `1.0000001^999999` (a line of 4.8 MB) takes 7.6 s. | Charging a body its static cost for each value (both branches of an `If`, a sampled function for each call around it) charged ordinary lists 6 to 300 times their work and made them undefined, while short exact decimals were not charged at all; charging the work done keeps the bound a bound on time. |

is needed within the stated bounds.

native CAS group verifies rational asymptotes and finite holes separately.
The dummy backend leaves the sine curvature vector undefined in the
historical group. The kernel evaluates it numerically.

`Roots` samples both explicit intervals and the active sampling window,
even for polynomials. It uses the construction's horizontal view scale and
falls back to the reference headless view when no view is supplied.

degree exceeds 25. Three-argument `If` uses the numerical path in
`Root`, `Roots` and `Extremum`. The reference `TurningPoint` still
requires a polynomial or a supported restricted polynomial.

`Root(function)` keeps products and integer powers factored when possible.
Dense polynomial expansion and Laguerre deflation are work-budgeted.

powers. The work budget governs the overall expanded degree.
The real polynomial command limits Laguerre to 100 evaluations per factor
and keeps exact zero roots if deflation fails, as the reference does.

The bracketed solver introduced in `b95f406` had tolerance defaults and
control flow consistent with the reference's third-party solver. This
revision implements the bracket updates and inverse interpolation from
[Brent, *Algorithms for Minimization without Derivatives* (1973), chapter 4](https://maths-people.anu.edu.au/brent/pub/pub011.html).
The EUPL command classes supply the seed and endpoint ordering,
defined-domain retry, and accuracy settings. The Java harness checks the
returned roots and Newton polishing, including when Brent returns an
endpoint.

The Runge–Kutta formulas come from [Dormand and Prince, *A family of
embedded Runge-Kutta formulae* (1980), table 2](https://doi.org/10.1016/0771-050X(80)90013-3)
and [Hairer, Nørsett and Wanner, *Solving Ordinary Differential Equations I*,
chapter II](https://doi.org/10.1007/978-3-540-78862-1), which describes
classical RK4 and adaptive step size selection. The Java harness compares
step times, accepted states and endpoints.

Curvature of general function and parametric inputs uses a five-point
finite difference of the kernel's first derivative where a second derivative
is needed.
